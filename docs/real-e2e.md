# Real local end-to-end exercise

This runbook is the single entry point for Callsheet's manual real-worker exercise (designs 12a-real-e2e, 12a-dev-flow-harness and 12a-dev-flow-verify). One command in one terminal runs one attempt of the full development flow: preflight, a local plane with three sidecars and the workspace hub, a headless Claude Code coordinator launched by the harness itself with your real configuration, the five-role workflow with its two bounded revision loops, your generation-qualified sign-off, the final candidate's deterministic validation, evidence collection, the offline check and a dynamic audit. It prints PASS or FAIL.

`reale2e run` selects the checked full development flow and writes the versioned evidence bundle `callsheet-dev-evidence/v2` with scenario `full` (design 12a-dev-flow-light; bundles recorded before it are `callsheet-dev-full-evidence/v1` and stay readable with their original full-only scope). `reale2e run-dev-light` runs one light attempt of the defect flow and `reale2e run-dev-exercise` runs one full then one light attempt as independent children of one combined exercise (see [Light attempt](#light-attempt) and [Combined exercise](#combined-exercise)). Its exits are 0 for a mechanical PASS, 1 for an executed failure or incomplete evidence, and 2 for a usage, gate or schema error. `reale2e run-dev-full` is a documented deprecated alias of `reale2e run`: the same checked full flow, the same arguments and the same exits 0/1/2. It no longer exits 3, and new runs no longer write `dev-execution.json`. This is a deliberate compatibility change of the run command.

A passing run demonstrates this installation's recorded mechanics (selections, admissions, transitions, waits, publications, owner receipts and the reviewer's execution) and the final candidate's deterministic feature checks on this machine at that time, with your own agent configuration. Mechanical PASS never means that a model's design, diagnosis or review was semantically approved: the judgment rows stay pending your external review. It is not a vendor or timeout qualification, not a sandbox containment claim, and it never changes the support catalog. It never runs in CI: the command refuses to start when a `CI` variable is present (even empty), without `CALLSHEET_REAL_E2E=1`, when `CLAUDE_CONFIG_DIR` is set (even empty: unset it yourself; the harness never does), or on any OS but Linux.

The owner records the live command, the merged revision, the qualification scope, the exercise and child paths and every paid call in the owner evidence under `design/`, not here. See [Codex triage qualification](#codex-triage-qualification) for the observed qualification and exercise records; historical evidence paths are not reusable output paths.

- Linux (live execution on any other system is refused: the harness requires Linux-qualified vendor installations and sidecars. The selected roles' postures do not decide this: the shipped selection is Codex and Claude only, both eligible on Linux and macOS, and that never bypasses the live Linux gate. Cursor's non-Linux refusal is `cursor worker execution is not qualified on this OS; consult the support catalog`. No jail and no non-Linux Cursor qualification has shipped).
- A required, eligible Grok installation, although no shipped role selects Grok: `--grok` stays mandatory, absolute and version-checked, and its idle sidecar is enrolled, deployed and cleaned up with the other two. This is a harness-wide prerequisite of the fixed executable, sidecar and version-record set (`claude, codex, grok, go, git`), not evidence that a Grok task ran. A missing or too-old Grok installation still stops before any paid work with the existing validation or preflight failure.
- For the optional Cursor coder only: an eligible Cursor executable (`cursor-agent`) at an absolute `--cursor` path on Linux, deployed as a fourth sidecar beside the idle Grok node, with version records `claude, codex, grok, cursor, go, git`; see [Cursor coder qualification](#cursor-coder-qualification).
- Built binaries: `go build -o /abs/path/callsheet ./cmd/callsheet` and `go build -tags reale2e -o /abs/path/reale2e ./cmd/reale2e`, run from inside the checkout.
- Go and Git on `PATH` (development prerequisites of the throwaway Go project, not Callsheet runtime requirements). The reviewer's verification helper and the final validation use the `go` the harness resolved, with an isolated offline environment and fresh caches.
- Logged-in vendor CLIs at or above the runtime minimum versions, given by absolute path: Claude Code `2.1.299`, Codex `0.162.1`, Grok `1.0.52`, Cursor `2026.10.01-e373342` (the adapter auto-mode version policy, independent of the historical catalog identities; Cursor's date baseline does not overcome its non-Linux gate). The harness never logs in, reads credentials or rewrites profiles: resolve login, model access, a supported model or posture outside it. Worker tasks request each tool's auto mode. A Linux Cursor worker passes `--trust --auto-review`, builds the model argument as MODEL-EFFORT and puts the prompt in one positional argument (32 KiB, visible to process inspection). Passing `--trust` may cause Cursor to maintain `~/.cursor/cli-config.json` and other state outside the task directory; the harness reports that file and does not treat it as owner configuration. The harness does not edit vendor configuration or retry a denial. `--trust --auto-review` is not a confinement claim.
- Costs and deadlines (policy, not measurements): five paid authentication preflights of at most 2 minutes each (one per role: triage and the code reviewer both preflight on the Codex sidecar under their own role IDs, even with the same model and effort); four paid workflow tasks on the happy path; the two bounded revision loops allow at most two extra design rounds, two extra fix rounds and two recovery dispatches, so at most fourteen workflow tasks and at most 19 worker calls including the five preflights, each workflow task at most 10 minutes from admission through publication; the headless coordinator adds vendor-dependent turns and tool calls in at most four phases; each owner decision window at most 20 minutes; the whole attempt within 90 minutes of preflight start (including the first fingerprint); the final candidate's validation shares one 60-second budget; then at most 2 minutes of cleanup. The theoretical task-time sum can exceed 90 minutes; the attempt deadline stops first. No automatic retries, no token-price ceiling and no currency estimate.
- Protected roots: each `--protect-root` directory (repeatable, absolute, existing, not nested in another, not inside the evidence or runtime directory) has every Git repository below it fingerprinted before and after the run. Discovery stops at each repository's working tree, whose status and tracked state (one streamed digest each) cover everything below it; a nested repository that its parent repository ignores is not separately protected. Discovery descends at most `--protect-depth N` directory levels below each root (default 3): deeper repositories and trees, such as a Go module cache, are not walked and not protected, and the report states the depth. A directory whose `.git` Git rejects is recorded by that entry's metadata, and any change to it fails. There is no default. With no `--protect-root`, only the four vendor homes are fingerprinted and the report says `No repository root was protected`.
- A quiescent owner environment: other Claude, Codex or Grok sessions writing configuration or repositories during the run make the comparison fail.
- The existing parent of a new evidence directory inside the checkout's ignored `design/` tree, for example `mkdir -p design/real-e2e-runs`. Evidence is bounded (64 MiB of text, 4 MiB of evidence repository) and stays local and private.

## Coordinator session

The coordinator runs with your user instructions, settings, permissions, skills, agents, plugins, hooks and login exactly as they are. The harness writes no agent configuration or settings file (the runtime MCP configuration and the evidence are its own files). Setting `CALLSHEET_REAL_E2E=1` is your authorization of session-only flags, identical in every coordinator phase:

- `--settings '{"sandbox":{"enabled":false}}'` merges over your settings for this session only. It is needed only because this exercise's plane listens on host loopback, which a sandboxed Bash command cannot reach (see [coordinator.md](coordinator.md)); it is not a general Callsheet requirement.
- `--permission-mode auto` requests Claude's automatic permission mode for this session only. Auto is available unless an administrator sets `permissions.disableAutoMode`. Supported models include Opus 4.6+ and Fable. The classifier pauses after 3 consecutive or 20 total blocks (owner-recorded, not a fresh upstream verification). The harness never edits that setting, never resets the classifier and never retries a denial. Exit 0 does not prove every requested action succeeded. Every init record of every phase must report `permissionMode` `auto`; the check never infers it from the launch flags.
- `--permission-prompts none` denies anything that would prompt. The permission mode still decides everything else. Print mode cannot answer a prompt.

There is no `--allowed-tools` list, no permission bypass, no second list and no tool filtering, and none of your rules or denies is removed: your inherited permissions stay active. Auto is a permission policy, not a containment claim. A bundle recorded with the earlier 15-rule `--allowed-tools` recipe is not evidence of this recipe: the checker rejects such a launch shape (`launch_shape_invalid`). Check a historical bundle with the revision that recorded it.

The exercise restricts the coordinator, by its prompt rather than by tool filtering, to exactly nine Callsheet MCP tools: `dispatch` (asynchronous, never with a wait), `task_ls`, `task_show`, `task_logs`, `task_cancel` (only this attempt's own dispatched tasks, after the attempt stopped), `ws_status`, `ws_diff`, `ws_push` (only the seed push, before the first dispatch; a light or both qualification probe makes exactly its two seed pushes and its one candidate push) and `ws_pull`. `task_wait` and every registration or workspace administration tool are forbidden; an unqualified wake ends the phase instead of the playbook's `task_wait` fallback. The offline check judges every recorded Callsheet call: the tool policy, the server's own argument rules (whatever the answer), exactly one result per call, and each successful answer bound to its request and to the captured plane task records, prepared plans, seed publication and evidence objects. A violation fails coordinator setup with `mcp_call_invalid` (a `task_wait` use with `coordinator_long_poll`). A well-formed call answered with an error is no evidence and never satisfies a gate; workspace inspection calls are optional, and any that are made must hold.

The command prints these flags and prerequisites before any vendor runs. A `reale2e` or runtime path containing `*`, `?`, `[`, `]`, `(`, `)`, a comma, CR, LF or NUL, or any character that would need shell quoting (a space or a quote, for example), is refused before any vendor starts (`permission_rule_invalid`). No Bash line of the coordinator prompt contains a redirect, `;`, `&&`, `|` or a quote.

The coordinator's helpers run in its Bash, read and write only fixed files of the live runtime, follow no symlink and make one exchange with the supervisor's single loop:

- `reale2e dev-next --run D` names the next prepared dispatch document (`prepared PATH SHA256`), the gate that ends the phase (`paused gate=KIND generation=N`), `complete`, or `pending` while the previous result is still being admitted. It never dispatches and never names an admitted plan again. Only a light or both qualification probe also answers `candidate_unpublished C` (exit 0) until its prepared light candidate C is on the light workspace's main branch.
- `reale2e dev-observe --run D --ordinal N --task ID` reports the task the coordinator dispatched for workflow ordinal N.
- Each task's background wait is exactly `R dev-wait-task --run D --task TASK_ID --ordinal N` (R the reale2e path): one simple command, run as the coordinator's harness-managed background job. Once the supervisor accepts that ID as ordinal N's only wait, it runs `callsheet task wait ID --until-done --json` itself and captures its output and exit under `D/coord/waits/NN`.

A denied tool call is never retried or widened: it fails the attempt, even when Claude exits 0. Resolve it in your own configuration and rerun.

Legacy-runtime compatibility helpers: `reale2e observe`, `reale2e wait-task` and `reale2e review-material` remain callable for legacy run files only (they refuse a development run file, and the development helpers refuse a legacy one). They are not this workflow's instructions.

## Reviewer verification helper

Each code review runs the fixed helper `reale2e dev-review-verify --task ID --candidate COMMIT --initial-source COMMIT --go ABS --deadline YYYY-MM-DDTHH:MM:SSZ` exactly once from its task checkout; the envelope supplies every value but the actual task ID. The `--deadline` is RFC 3339 UTC at whole seconds with a `Z` suffix (the attempt deadline rounded down); any other spelling is refused. The helper is a fixture-specific test runner, not a reviewer: before running anything it refuses pre-existing scratch, a symlinked or wrong checkout, a missing commit, a modified input (an in-progress `review.md` aside) or an unexpected file (one Callsheet runtime directory `.callsheet-runtime-<32 lowercase hex>`, never read, and empty real `.agents`, `.aws` and `.codex` directories aside; the receipt names a rejected entry and its kind); it exports the pinned candidate from the checkout's own objects into a fresh `.callsheet-review-scratch/<task-id>/after/`, runs `go test ./...`, `go test -coverprofile=<scratch>/coverage.out ./...` and `go test -json -count=1 ./...` there with the pinned Go in an isolated offline environment, derives the changed-code coverage, digests the export as written and again after the commands (a command that changed, removed or added an export entry fails the run with `export_changed`; both manifests stay in the receipt), removes only its own scratch and verifies its absence and the unchanged inputs, and prints one JSON receipt line of at most 64 KiB followed by review.md's report lines (at most 8 KiB): the reviewed candidate, the source digests, the two verification commands with their exits, the coverage, the cleanup flags and the receipt line's SHA-256, which the reviewer pastes verbatim (exit 0 passed, 1 executed failure, 2 invalid invocation). When a publication is rejected, its reason and the rejected review.md (at most 32 KiB) are kept in the task's evidence as `publication-rejection.json` and `rejected-review.bin`. The offline check (and the qualification check, for the reviewer probe) binds them to the task, its plan, its result commit and the attempt's stop, and reruns the review checks on a complete retained review.md; a refusal it cannot recompute from what was retained is reported unobserved. They never change the verdict.

A light review runs the same helper with `--scenario light` appended (`reale2e dev-review-verify --task ID --candidate COMMIT --initial-source COMMIT --go ABS --deadline YYYY-MM-DDTHH:MM:SSZ --scenario light`; without `--scenario` the historical full recipe runs). Under `.callsheet-review-scratch/<task-id>/` it exports the seed to `baseline/`, the seed with the candidate's complete `main_test.go` to `before/` and the candidate to `after/`, runs `go version`, the baseline `go test -count=1 ./...` and `go test -count=1 -covermode=set -coverprofile=<scratch>/coverage.out ./...`, the red `go test -count=1 -json ./...` on `before/` and the green one on `after/`, then the candidate suite and coverage, digests each export as written and after the commands (`export_changed` otherwise), and prints its `callsheet-dev-light-review-run/v1` receipt and the light report lines: the source and test digests, six `Verification exit` lines (the red line states the expected exit 1 and the expected assertion failure of `TestRun/whitespace`), the covered/total coverage comparison, the cleanup and the receipt digest. A full receipt never stands in for a light review, or the reverse.

The reviewer still reads the design, code and tests and judges every FP. `review.md` names the receipt in one plain line `Reviewer run sha256: <64 lowercase hex>` (the SHA-256 of the helper's complete JSON output, including its final LF), besides its reviewed candidate, source hashes, both verification commands with their exits, the coverage and the cleanup. The supervisor corroborates the receipt only from the reviewer's complete, untruncated task log: exactly one top-level command record of exactly that command. An approval needs a complete successful receipt; a failed receipt can support changes requested; prose alone never proves execution.

## Light attempt

```sh
CALLSHEET_REAL_E2E=1 /abs/path/reale2e run-dev-light \
  --callsheet /abs/path/callsheet \
  --claude /abs/path/claude --codex /abs/path/codex --grok /abs/path/grok \
  --protect-root /abs/projects \
  --evidence /abs/callsheet/design/real-e2e-runs/NEW-LIGHT
```

A light attempt takes the same arguments, gate and protections as `run`. Its seed is the committed fixture `internal/reale2e/testdata/devlight-seed`: the known-good greeting with one seeded defect (`strings.TrimSpace(*name) == ""`, so `--name " "` exits 2 with `greeting: --name must not be empty`) and the nine-case `TestRun` table without its `whitespace` row; its `FEATURE.md` starts with the light request and keeps the ten-case contract. Before any paid call the supervisor proves the seed exhibits exactly that defect (otherwise it stops `light_seed_invalid`), then shows the attempt ID, the seed commit and tree, the `FEATURE.md` and role-selection digests, the authorized scope `whitespace-restoration/v1` and the disclosure, and asks:

```
Authorize light investigation and restoration for attempt ID? Type exactly "light ID" or "no ID".
```

Answer `light <attempt-id>` or `no <attempt-id>` as a fresh line within 20 minutes. This intake is not a design sign-off: it authorizes triage's investigation, the frozen coder's restoration in defect mode and the bounded fix and re-triage loops, never a design or an escalation. No, end of input, expiry, a wrong ID or input typed before the prompt stops with no paid call; the decision is kept in `intake/decision.json` and only a light decision writes `intake/receipt.json`.

The light workflow runs in one coordinator phase: triage (rca.md, and a fix.md only at `TRIAGE_CONFIRMED` or `TRIAGE_PROBABLE` with one `Confidence:` line, one `Design required:` line and exactly one plain `Root cause: main.go:N` or `Root cause: main_test.go:N` line naming an existing line of the seed), the coder in defect mode, then the executing light review. `REVIEW_CHANGES_REQUESTED` runs the same coder in fix mode; `DESIGN_QUESTIONS` and `NEEDS_TRIAGE` re-triage. Caps: one initial triage and coder/review pair, at most two additional fix/review pairs and at most two recovery dispatches, so at most nine workflow tasks and 14 paid worker calls with the five preflights; the happy path is 8 calls. `Design required: yes` or `NEEDS_DESIGN` stops with `needs_design` and a next-step handoff for a separately authorized full design flow; nothing is designed in a light attempt. The same 10-minute task, 90-minute attempt, 60-second final validation and 2-minute cleanup bounds apply, with no retry.

The final validation exports the seed and the candidate and runs the candidate's whole `main_test.go` byte for byte on both: red means exit 1 with exactly `TestRun/whitespace` failing and the nine others passing (no build failure, panic, timeout or skip), corroborated by the seed's own CLI result; green means exit 0 with all ten passing. Assertion messages are never matched. It then runs the candidate suite, the ten CLI cases and the coverage comparison: both sides run `go test -count=1 -covermode=set -coverprofile=<scratch>/coverage.out ./...` over `example.com/greeting/main.go`, and the candidate passes exactly when candidateCovered×baselineTotal ≥ baselineCovered×candidateTotal (`coverage_decreased` otherwise). The nine-case seed suite and the ten-case final suite differ by design. The light report adds the criteria `light_intake`, `triage_brief`, `regression_red_green` and the light `coverage`, and the audit rows `intake/authorization`, `task/NN/triage-brief`, `validation/seed-defect`, `validation/regression-red`, `validation/regression-green` and `validation/coverage-comparison`; each triage's causal evidence and brief content, each candidate's regression assertions and restoration scope and each review's reasoning stay judgment rows for your external audit.

### Light triage scratch

## Sign-off

After an approving design audit and the coordinator phase's exit, the same terminal shows the full approved `design.md`, `revision-history.md` and `design-review.md` with their paths and SHA-256 digests, then asks, with N the actual design generation:

```
Approve design generation N and start coding? Type exactly "yes N" or "no N".
```

Answer `yes <generation>` or `no <generation>`, exactly. A plain `yes` decides nothing, and neither does a line naming another generation (the window's deadline is unchanged); input typed while no window is open is discarded. A yes records a generation-qualified receipt and resumes the same coordinator session for coding and the code review. A later design revision invalidates the receipt at the designer's dispatch, even when its bytes are unchanged, and needs a fresh audit and a fresh decision. No, end of input or the 20-minute window ending (never past the attempt deadline) ends the attempt without coding. A designer's clarification question is answered with `answer <generation> <text>` (one line, at most 8192 bytes, no secrets).

## Reading the result

The final output prints PASS or FAIL for the mechanical and deterministic criteria and, separately, `Result judgments: needs owner/coordinator review`, then links `report.txt` and `audit.md` in the evidence directory.

- `report.txt` lists every criterion (manifest, provenance, roles, preflight, coordinator setup, admissions, transitions, waits, publications, owner receipts, reviewer execution, baseline, final tests, coverage, feature oracle, cleanup, owner environment, deadlines, cost) with its fixed failure codes, or, when the attempt verifiably stopped before a criterion's step, `not_reached` with the stopping cause; the run still fails. It lists the protected roots, the protected changed paths (any one fails the run) and the tool-maintained changes (report-only), counted as added, changed and deleted per vendor and top-level directory (`.` for files directly in the vendor home).
- `audit.md` (and `audit.json`) walks every actual step in order with stable row IDs: the setup, each preflight and phase, every task's dispatch, wait, publication, marker and (for a code review) reviewer execution, every transition, decision and receipt, the validation and each CLI case, cleanup, the environment comparison and the accounting, each `correct`, `incorrect` or `unobserved` with evidence pointers; the next blocked step of a stopped attempt is `unobserved` with its cause, and nothing is invented for loops that did not happen. A separate judgment layer (each design's completeness, each audit's quality, each implementation's assertions, each review's quality, each triage's causal evidence) stays `unobserved` until reviewed.
- `cost.json` lists every admitted worker call, failed ones included, every phase, the owner windows, the attempt and the cleanup. Provider usage is `unknown` unless provider-reported; nothing is estimated.

Only your repositories and this exact owner-configuration list are protected; any change to them, a removal, a replacement by another file type or link, or an addition fails the run (`owner_environment_modified`), and listed directories cover every descendant:

| Vendor home | Owner configuration |
|---|---|
| `~/.claude` | `CLAUDE.md`, root `settings*.json`, `agents/`, `skills/`, `commands/`, `hooks/`, `plugins/installed_plugins.json`, `plugins/blocklist.json`, `plugins/config.json` |
| `~/.codex` | root `AGENTS*.md`, `instructions.md`, `prompts/` |
| `~/.grok` | `config.toml`, `managed_config.toml`, `settings.json`, `user-settings.json` |
| `~/.cursor` | `mcp.json` |

An owner-configuration entry changes only when its content, type, mode or link target differs: a tool rewriting a listed file with identical bytes (a new inode and timestamps) is no change, while a same-size content change still fails, because these files are content-hashed. A listed file over 1 MiB is fingerprinted by metadata only, so its size and modification time stand in for its content. The vendor homes must stay the same real directories (a home may be created during the run, not removed or replaced), and the `plugins/` directory must stay a real directory; size and timestamp changes caused by their children are fine. Everything else in a vendor home is tool-maintained, whatever its name or type: session transcripts, history, logs, caches, state databases, token refreshes and Cursor files other than `mcp.json`. `~/.cursor/cli-config.json` is one of those: Cursor maintains it, and the harness reports it without failing the run. `~/.cursor/mcp.json` stays owner configuration. A first normal run is expected to list such changes; they are reported as counts only and never fail the run. Their per-entry metadata (no contents) is detailed in `environment/diff.json` up to its 4 MiB bound, and the report and audit state how many entries were omitted beyond it. These are accepted coverage exclusions, shown together in `report.txt` on passing and failed runs alike:

```
not covered: ~/.claude.json
not covered: ~/.claude/.config.json (Claude state file; holds per-project tool grants, MCP-server lists and trust flags)
not covered: ~/.claude/backups/.config.json.backup.* (backups of Claude state, including per-project grants)
not covered: ~/.codex/config.toml (Codex records a trust entry per working folder)
not covered: untracked .claude/ directories inside protected repositories
not covered: ~/.claude/plugins/known_marketplaces.json (Claude refreshes marketplace timestamps)
not covered: ~/.cursor/cli-config.json (Cursor maintains this file; report-only)
```

## Rerun

Resolve the reported cause (login, model access, a permission or configuration incompatibility, a protected change), then run the same command with a new evidence directory. Every attempt has its own run ID, runtime, workspace and coordinator session; nothing is resumed or retried, and earlier bundles keep their result. A later attempt after a failure needs fresh owner authorization. If cleanup could not prove every process stopped, the runtime is kept and the supervisor prints the process IDs to check and stop before rerunning.

## Evidence bundle

The bundle's `manifest.json` carries the schema `callsheet-dev-evidence/v2` and its scenario (`full` or `light`; historical bundles carry `callsheet-dev-full-evidence/v1`), the run's provenance, the frozen selections, the attempt window, the harness executable's SHA-256 before and after, the stop and the final candidate and review, and the inventory of every primary file and stored Git object. Every structured record is a strict schema-bearing envelope; the layout is closed (every plan, dispatch document, task view, log, observation, admission, record, wait, review evidence, transition, decision, receipt, phase stream, launch record, the admissions sweeps, the cleanup and cost records, the validation records and an evidence repository with `refs/heads/seed` and `refs/heads/task-NN`). The checker replays the policy from the seed, rebuilds every envelope, re-admits every publication, re-derives every session fact and reviewer receipt and the final oracle, and compares the stored report and audit byte for byte. Checksums provide consistency, not signatures: the checker does not claim cryptographic proof of a paid run.

Captured source documents and fixture files are stored inertly: a logical capture `L` is stored at `_captured/L.bin` (for example `setup/sources/docs/examples/dev-flow/triage-runbook.md` at `_captured/setup/sources/docs/examples/dev-flow/triage-runbook.md.bin`), with its logical path, byte length, SHA-256, origin and computed `storage_path` in the provenance records. `go help packages` says directories and files beginning with `.` or `_` are ignored by the go tool, so a new bundle under the checkout adds no Go package and needs no `go.mod` workaround; `.bin` bytes count against the same text budgets, and distinct captures that collide under ASCII case folding are refused. A v1 bundle is read at its original raw paths with no migration, so its old captures may still affect package discovery: move an old bundle outside the module yourself if you want, preserving its bytes. The harness never deletes your workaround or modifies old evidence.
